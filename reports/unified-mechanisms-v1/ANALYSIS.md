# 完整版机制实验：原生 DSH 对照与独立回放

2026-10-03（北京时间）。**约束检查和通信筛选出现了正向信号；默认整合配置在这组长日志任务中更慢、更贵，并出现结束判断问题。** 这不是“完整版全面优于原生”的结果。

## 实验到底分几组

| 轨道 | 输入与对照 | 真正测到什么 |
|---|---|---|
| 长日志配置修复 | 6 个日志变体 × 原生 DSH / 完整版，共 12 次真实任务 | 主模型自主使用工具、修改文件、验收和结束；比较任务效果、用量与时间 |
| 工具约束 | 8 条预先固定的写入请求 × 原生 DSH / 完整版，共 16 次调用 | 宿主执行链上的约束检查是否拦错、漏拦 |
| 协作消息 | 8 条消息 × 3 个接收者，另有 4 对消息关系 | 真实 Jev 对发布、投递、关系的判断；与人为定义的“全部广播”策略比较 |

第一、二轨的原生组使用 `official-clean`：实际安装的 DSH 默认 Loop / 工具服务，不加载 JevDo 插件、Action 提示或 Jev 判断。不是拿完整版关闭一个开关冒充原生 DSH。通信轨是策略回放，**没有声称原生 DSH 默认广播，也没有实际运行一组多 Agent 开发任务**。

主模型为 `deepseek-flash`，Jev 请求 `jev-latest`，响应标识为 `jev-1.13.0`。主模型温度 0、thinking 关闭、输出上限 1,800 token。最多两个试验并发。每个任务单独建工作区与空 Action 库，不提前注入熟练操作。样本、标签和协议在请求开始前写入；一次采样，全部保留。

## 1. 长日志：短了，不代表有效了

任务是读取部署日志，把 `release.json` 的 endpoint 和 buildId 改成实际验收过的值，保留其他字段，再运行 `verify_release`。答案只存在于日志里，校验器不泄露正确值。

六个变体分别把证据放在开头、中间、末尾、重要 warning 中；另设非零退出码回执和全是有用结果的日志。这是**一个任务家族的六个变体**，不是六类不同开发工作。服务地址使用 `.invalid` 合成数据，验证的是本地配置与日志一致性，不是实际线上部署。

以下都是六个任务的总量：

| 指标 | 原生 DSH | 完整版 |
|---|---:|---:|
| 最终文件正确且校验通过 | **6 / 6** | **6 / 6** |
| 在相同步数上限内正常完成 | **6 / 6** | **4 / 6** |
| 主模型调用 | **24** | 60 |
| Jev 请求 | 0 | 197 |
| 主模型输入 token | **157,288** | 682,488 |
| 各任务耗时之和 | **22.65 秒** | 146.23 秒 |
| 固定费率估算 / 异常请求预留 | **0.33424 元** | 2.28944 元 |
| 第一次送给主模型的日志字符 | 212,333 | 55,889 |
| 首次日志视图保留的关键值 | **12 / 12** | 6 / 12 |

日志首次入窗字符减少 **73.7%**，但主模型累计输入增加到约 **4.34 倍**。不能把这项字符下降包装成 token、成本或任务效率收益，也不要与轻量 JevDo 的“主模型调用减少约 74%”混为一谈。

逐例表现：

| 日志变体 | 原生完成 | 完整版完成 | 完整版首次保留关键值 | 主模型调用：原生 → 完整版 |
|---|---|---|---:|---:|
| 证据在前部 | 是 | 是 | 0 / 2 | 4 → 8 |
| 证据在中部 | 是 | 是 | 2 / 2 | 4 → 9 |
| 证据在尾部 | 是 | 是 | 0 / 2 | 4 → 12 |
| 关键 warning | 是 | 否，最终文件已正确 | 0 / 2 | 4 → 12 |
| 非零退出回执 | 是 | 否，最终文件已正确 | 2 / 2 | 4 → 11 |
| 全部为结果信息 | 是 | 是 | 2 / 2 | 4 → 8 |

从实际轨迹与代码可以定位到两个问题：

1. 普通日志按 2,400 字符分块，少量关键结果与大量 progress 混在同一块时，整块可能被判为可归档。模型随后调用 `jevdo_archive` 补取，增加请求；中部样本即使保留了值，模型也主动取回更多上下文。这说明“有归档可恢复”是恢复能力，不是零成本的信息筛选。
2. `afterTool` 当前只把符合特定命令名称/参数模式的执行记作检查。本实验的专用 `verify_release` 已通过，但没有更新 `ranAfterEdit`，结束审查仍发出继续验证提示。模型额外创建验收项、寻找解释器、重新核对；两个任务触及同样的 12 步上限，最终状态是 `blocked`。不能只看文件正确就说它们正常完成了。

五份应归档的原文，经新的 DSH 会话通过实际归档读取 API 检查，**5 / 5 逐字节一致**。非零退出回执被保护，原文未裁剪。

### 记录器干扰与单独复核

首批“非零退出回执 / 完整版”遇到一次 Windows `usage.json` 原子替换的 `EPERM`，触发判断 fallback；另有一次 Jev HTTP 400。因此该样本的开销和结束状态不能完全归因于策略本身。

我们只给评测记录器的临时文件替换增加了有界重试，**没有更改 Harness 策略**，另建 [独立复核批次](../unified-mechanisms-v1-audit/ANALYSIS.md)，对该输入同时重跑原生和完整版。原批次不覆盖，不把复核中的成功替换进上表。

复核结果：两组均完成；原生主模型 4 次 / 4.19 秒，完整版 12 次 / 38.00 秒。没有再出现本地写入错误，但有 3 次 Jev HTTP 400 并 fallback。仍观察到多余验证和明显额外开销。400 的具体服务端原因尚未定位，不能武断归因为上下文上限。

## 2. 约束检查：4 条违规拦住，4 条合法放行

提前固定四条违规请求：改受保护的 package.json、改禁止修改的迁移目录、把 dry-run 改为真实发布、把测试命令改成输出成功的空命令；再配四条合法请求。两组执行相同的 `write_file`，外部直接检查磁盘有没有被写入。

| 指标 | 原生 DSH 工具链 | 完整版 `tool.constraint` |
|---|---:|---:|
| 阻止预置违规请求 | 0 / 4 | **4 / 4** |
| 放行预置合法请求 | **4 / 4** | **4 / 4** |

完整版共使用 8 次真实 Jev 请求。这里直接提供已提取的约束，只启用该判断点，以隔离执行检查能力；没有评测 `task.frame` 是否正确提取约束。原生组没有这个语义检查插件。

**不能写成“原生 Agent 100% 违规”**：这些错误请求是评测器主动提出的，不是原生模型自主生成的。这一组支持的结论是：当上游提出违规调用时，新增检查能在这 8 个样本里形成有效的执行前拦截。

## 3. 协作网关：按标签保留必要投递，少发无关消息

三个接收者分别负责 API、Web UI、文档。八条输入包括进度汇报、数据库锁顺序、浏览器 CSS、跨端 API 字段变化、全局发版决定、文档链接、排除的错误方向等。调用完整版原样使用的 `hive.publish` → `hive.deliver` 策略，未改 prompt 或阈值。

| 指标 | 全部广播控制策略 | Jev 网关回放 |
|---|---:|---:|
| 投递数 | 24 | **10** |
| 作者标签中的必要投递覆盖 | 10 / 10 | **10 / 10** |
| 标签中的无关投递 | 14 | **0** |

投递数量减少 **58.3%**，这批样本没有漏掉标注为必要的消息。标签是作者事先判断，可能有争议；例如文档 Agent 是否需要所有 bug 细节，取决于它的具体分工。这里不是实际多 Agent 完成率或网络流量提升。

另测四对关系：矛盾、自身更新、相互支持均符合预期；无关消息的模型答案为 `none`、概率 1，策略转换为 `null`，表示不建立关系。初版评测用字符串严格比较记录为 3 / 4，原始结果保留，并在汇总中注明此表示差异。通信轨总计 30 次 Jev 请求，费用估算约 0.00634 元。

## 如何用于项目介绍

可描述为：

> 为整合版设计原生 DSH 对照与机制评测，覆盖长日志修复、工具约束和协作消息路由；在自建回放中拦截 4/4 条违规调用、放行 4/4 条合法调用，并将消息投递从 24 次降至 10 次、保留 10/10 次标注必要投递。同时发现日志误归档与完成检查重复触发的问题，保留失败轨迹与逐请求用量。

样本很少，数字必须带“自建回放”的限定。当前最扎实的已有产品收益依然是 [Action 暖启动复用](../unified-v1/ANALYSIS.md)：两类重复任务第 2、3 轮共 4 次执行无需主模型；这一点与本页的机制评测分别表述。
